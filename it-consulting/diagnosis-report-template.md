# 진단 리포트 템플릿 — "구조적 리스크 3가지 + 우선순위"

의뢰인에게 전달하는 산출물의 표준 포맷. 매 건마다 이 구조를 채워서 사용한다.

---

## 0. 표지 / 개요

- 서비스명 / 의뢰인명
- 진단 범위 (예: DB 설계, API 구조, 배포, 보안 기초 중 어디까지 봤는지)
- 진단 일자
- 사용한 정보(코드 리포지토리, 인터뷰 내용, 제공된 문서 등) — 무엇을 근거로 판단했는지 명시

## 1. 현황 요약 (3~5줄)

- 지금 시스템이 하고 있는 일과 규모(트래픽, 데이터량, 사용자 수 등 파악된 범위 내)를 객관적으로 요약
- "잘 되고 있는 부분"도 1~2가지 짚어서 균형 잡힌 진단이라는 신뢰를 준다

## 2. 구조적 리스크 Top 3

각 리스크마다 아래 4개 항목을 동일한 형식으로 반복:

### 리스크 #N: [한 줄 제목]

- **현재 상태**: 무엇을 어떻게 하고 있는지 (사실 기술, 비난 톤 금지)
- **왜 문제인가**: 방치했을 때 구체적으로 어떤 상황에서 무엇이 터지는지 (예: "동시 접속자 OO명 넘으면 커넥션 풀 고갈로 응답 지연")
- **우선순위 근거**: 발생 확률 × 영향도 기준으로 왜 이 순위인지 1~2문장
- **개선 방향 (실행 X, 방향만)**: 구체적 구현이 아니라 "이런 접근이 있다"는 방향 제시. 실행은 의뢰인 몫임을 리포트 전체에서 일관되게 유지.

> 우선순위 판단 기준 예시:
> - 1순위: 데이터 유실/보안 사고처럼 되돌릴 수 없는 리스크
> - 2순위: 서비스 성장 시 병목이 될 구조적 문제
> - 3순위: 지금 당장은 안 터지지만 기술 부채로 누적되는 문제

## 3. 개선 로드맵

| 구분 | 기간 | 항목 | 관련 리스크 |
|---|---|---|---|
| 단기 (즉시 조치) | ~1주 | | |
| 중기 | 1~2개월 | | |
| 장기 (구조 개선) | 3개월+ | | |

- 로드맵은 "무엇을 언제 할지"까지만. "어떻게 구현할지"는 의뢰인의 실행 영역이므로 세부 코드/설정값은 포함하지 않는다.

## 4. 참고 체크리스트 (진단 시 확인 항목, 부록)

- DB 설계: 정규화 수준, 인덱스 여부, 백업/복구 전략, N+1 문제 여부
- API 구조: 인증/인가 방식, 버저닝, 에러 응답 일관성, Rate limit 여부
- 배포: CI/CD 유무, 환경 분리(dev/staging/prod), 롤백 가능 여부
- 보안 기초: 시크릿 관리, HTTPS 적용, 의존성 취약점, 입력값 검증

## 5. 클로징

- 리포트 유효 범위(제공된 정보 기준이며 실제 트래픽/장애 데이터와는 차이가 있을 수 있음) 명시
- 후속 Q&A 안내 문구
