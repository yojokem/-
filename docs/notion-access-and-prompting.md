# Notion 접근 · 입출력(I/O) · 프롬프트 운용 가이드

이 저장소에서 Claude가 Notion을 다루고 사용자와 입출력을 주고받는 방식을 정리한 문서다. 커넥터별 ID·속성은 `CLAUDE.md`의 "커넥터 메모"가 원본이고, 여기서는 중복하지 않는다.

## 1. Notion 접근 (MCP 커넥터)

### 1.1 도구 사용 순서
- 쓰기 전에 항상 `notion-fetch`로 대상 DB의 스키마를 읽는다. 속성 이름과 select 옵션은 fetch 결과 그대로 쓴다.
- DB에 행을 만들 때는 DB ID가 아니라 `collection://…` URL을 `data_source_id`로 넘긴다.
- 지연 로드되는 도구는 `ToolSearch`에서 `select:<이름>`으로 스키마를 먼저 불러온다. 안 불러오면 호출이 InputValidationError로 실패한다.
- 검색은 `notion-search`(키워드, `page_size`로 결과 수 제한). 필터·정렬 일부는 Business 플랜 전용이라 쓰지 않는다.

### 1.2 속성 쓰기 규칙
- 날짜는 `date:<속성>:start`, `:end`, `:is_datetime`으로 쪼개 넣는다.
- 숫자는 JS 숫자로, 체크박스는 `__YES__`/`__NO__`로 넣는다.
- multi_select는 JSON 배열 문자열(예: `["개인"]`)로 넣는다.
- 관계(relation)는 페이지 URL 배열로 넣는다.
- 이름이 `id`나 `url`인 속성은 `userDefined:` 접두사를 붙인다.
- 페이지 본문은 쓰기 전에 `notion://docs/notion-flavored-markdown-spec`을 읽는다. 표 같은 블록은 문법이 달라서 추측하지 않는다.

### 1.3 읽기의 한계 (이 세션에서 확인한 것)
- `fetch`는 수식(formula) 속성의 값을 돌려주지 않고 `formulaResult://…` 참조만 준다.
- `query-data-sources`(SQL)도 수식 컬럼은 조회할 수 없다(`notAvailableInQuerySql`에 나열됨).
- 따라서 수식 검증은 (1) 수식 식을 손계산과 대조하거나 (2) 사용자가 Notion 화면에서 값을 확인하는 방식으로 한다. 값을 확인하지 못했는데 "검증됐다"고 쓰지 않는다.
- 수식 결과가 꼭 필요한 자동화라면 수식 대신 Claude가 계산해서 숫자 속성에 직접 쓰는 방식을 고려한다.

### 1.4 생성·수정 시 원칙
- 페이지·DB 생성은 외부 쓰기다. 위치를 사용자가 지정하지 않았으면 `creation_mode: "draft"`로 비공개 페이지를 만들고, 비공개라는 사실과 이동 가능 여부를 알린다.
- 삭제·대량 수정·공유 변경은 먼저 확인한다(`CLAUDE.md` 작업 규칙).
- 기존 구조(상태, 자동화, 처리 주체 옵션)는 바꾸지 않고 그대로 따른다. 새 옵션이 필요하면 사용자에게 먼저 묻는다.
- 테스트용 행에는 `[검증]` 같은 접두어를 붙여서 나중에 지우기 쉽게 한다.
- 건강·환자 관련 개인 데이터는 이 저장소에 커밋하지 않는다. 저장소에는 명세와 스크립트만 두고, 기록 자체는 Notion에 둔다.

### 1.5 "할 일 관리" DB 운용
- 작업을 만들면 처리 주체와 자동화 값을 반드시 채운다.
  - 사용자가 결정해야 하는 일: 처리 주체 `사용자 직접`, 자동화 `확인 필요`.
  - Claude가 초안까지만 하는 일: 처리 주체 `Claude-메인세션`, 자동화 `초안만`.
  - 되돌리기 쉽고 승인된 반복 작업만 `자동 실행`.
- 메모에는 "무엇을 결정해야 하는지"를 한두 줄로 적고, 관련 페이지에 링크를 단다.

## 2. 사용자 상호작용(I/O) 설계

### 2.1 일반 원칙
1. **입력은 최소로**: 사용자가 반복해서 치는 값은 필수 필드만 남기고, 나머지는 기본값이나 기억된 값으로 채운다.
2. **직렬화해서 보여 주기**: 자유 문장을 받으면 구조화 데이터(JSON)로 바꿔서 보여 주고, 확정 후에 기록한다. 사용자는 해석이 맞는지만 확인하면 된다.
3. **모호하면 객관식으로**: 빠진 값이나 해석이 갈리는 값은 `AskUserQuestion`으로 닫힌 선택지를 준다. 서술형 질문은 피한다.
4. **쓰기 전 확인, 쓴 뒤 보고**: 외부로 나가는 쓰기는 확정 뒤에만 한다. 결과는 링크와 함께 한 줄로 요약한다.
5. **미확인은 표시**: 원문으로 확인되지 않은 수치·기준은 "미확인"이나 "임의 가정"으로 명시한다.

### 2.2 AskUserQuestion 사용법
- 한 번에 질문은 최대 4개, 질문당 선택지는 2~4개다. 4개를 넘기면 호출이 거부된다.
- "기타(Other)"는 자동으로 붙으므로 따로 만들지 않는다.
- 권장안이 있으면 첫 번째 선택지로 두고 라벨 끝에 `(Recommended)`를 붙인다.
- 질문은 단독으로 이해되게 쓴다. 사용자가 질문 창만 볼 수 있으므로, 대상 항목 이름과 배경을 질문 안에 넣는다.
- 사용자가 "네가 연구해서 정해라"라고 하면 근거와 함께 하나를 정해서 진행하고, 정한 내용을 결과 보고에 명시한다.
- 질문이 4개를 넘으면 영향이 큰 것부터 묻고, 나머지는 권장안으로 확정해서 알린다.

### 2.3 입력 규약 예시 (IEMI 운동 로그)
- 한 줄 입력: `32회 RIR2 식후40분` (선택: `근육 38.5`)
- 직렬화 JSON: `{"date","reps","rir","glucose","gap_min","muscle_kg","week_n"}`
- 모호값 처리: 식후 30분 미만, RIR 소수 등 → 객관식 질문
- 확정 후 기록 → 점수와 구성요소, 주간 누적, 직전 대비 증감을 한 줄로 응답
- 모델 명세와 미확정 항목은 Notion의 "IEMI 운동 지수" 페이지가 원본이다.

## 3. 프롬프트 운용 방식

### 3.1 지시를 구체화하는 순서
1. 요청에서 확정된 것과 정해지지 않은 것을 나눈다.
2. 정해지지 않은 것 중 관례·조리상 보충하거나 빼야 하는 항목, 보정이 필요한 항목을 골라낸다.
3. 되돌리기 어렵거나 사용자의 의도가 갈리는 항목만 되묻는다. 나머지는 권장안으로 진행하고 결과에서 알린다.
4. 확정한 항목을 문서나 DB(할 일 관리)에 남겨서 다음 세션이 같은 질문을 반복하지 않게 한다.

### 3.2 외부 모델 출력(예: Gemini 대화)을 다룰 때
- 받은 수식·수치는 그대로 구현하지 않고 먼저 내부 일관성을 점검한다(배점 합계, 값 범위, 예시와 정의의 불일치).
- 점검에서 나온 문제는 목록으로 보여 주고 사용자가 결정하게 한다.
- 생리학·의학적 근거가 원문으로 확인되지 않은 부분은 "미확인"으로 표시하고, 실제 효과를 뜻하는 수치처럼 보이게 쓰지 않는다.
- 검증용 예시(입력·기대 출력)는 DB에 테스트 행으로 넣어서 수식이 의도대로 나오는지 대조한다.

### 3.3 서브에이전트
- 서브에이전트 조사는 원문을 열지 못하고 검색 요약만 본다. 결과는 근거가 아니라 보고서로 취급하고, 사용자가 가져온 원문으로 다시 대조한다.
- 사용자가 요청하지 않으면 서브에이전트를 띄우지 않는다. 대부분의 작업은 본 세션에서 직접 처리한다.

### 3.4 응답 형식
- 한국어 반말, 핵심 위주의 목록 구조(①, A, ◦ 등)로 쓴다.
- 예외 사항, 주의 사항, 사람이 보기에 설명이 필요한 부분만 길게 쓴다.
- 확인하지 못한 것은 확인하지 못했다고 쓰고, 끝난 것은 끝났다고 쓴다.
